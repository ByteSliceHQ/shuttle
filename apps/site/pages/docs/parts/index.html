Build your own ADE

Shuttle's interface is a set of React parts: a session, its conversation, the composer, the artifacts pane, the agents. Shuttle's own web and desktop apps are only one way of putting them together. Put them together your way, with your own layout, your own parts beside ours, and your own kinds of tab.

The example Host the engine

How it fits together

There are three layers. A host says how to reach the backend. The provider gives every part the host, your router and who is signed in. A session follows one session's run, folds its events once, and hands the result to every part inside it. The parts take no session props of their own, so you can arrange them however you like.

A first ADE

A conversation on the left, artifacts on the right, and no sidebar. This is all it takes once you have a backend to point at: Shuttle's own Worker, or one of yours running the engine. 

bun add @swirls/shuttle @tanstack/react-query
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'
import { Suspense } from 'react'

import { createShuttleHost, Shuttle } from '@swirls/shuttle/react'
import { TooltipProvider } from '@swirls/shuttle/react/ui'

const host = createShuttleHost({ baseUrl: 'https://shuttle.example.com' })
const queryClient = new QueryClient()

export function MyADE({ sessionId }: { sessionId: string }) {
  return (
    <QueryClientProvider client={queryClient}>
      <TooltipProvider>
        <Shuttle.Provider host={host} router={router} identity={identity}>
          <Suspense fallback={<p>Opening…</p>}>
            <Shuttle.Session id={sessionId}>
              <div className="grid h-dvh grid-cols-[1fr_420px] grid-rows-[auto_1fr]">
                <div className="col-span-2">
                  <Shuttle.SessionHeader />
                </div>
                <main className="flex min-h-0 flex-col">
                  <Shuttle.Conversation />
                  <Shuttle.Composer />
                </main>
                <aside className="min-h-0 border-l">
                  <Shuttle.Artifacts />
                </aside>
              </div>
              <Shuttle.Palette />
            </Shuttle.Session>
          </Suspense>
        </Shuttle.Provider>
      </TooltipProvider>
    </QueryClientProvider>
  )
}

Shuttle.Session suspends while it opens the session's run, so give it a Suspense boundary. Where the router and identity come from is covered in Fitting it into your app.

The parts

Part What it does
Shuttle.Provider Gives the parts the host, the router and who is signed in. Everything goes inside it.
Shuttle.Session Follows one session and gives it to the parts inside.
Shuttle.SessionHeader The session's title, status and controls.
Shuttle.Conversation The conversation with the agents, with turns streaming in as they are written.
Shuttle.Composer Where you write to the agents and steer them while they work, with @-mentions for files, sessions and agents.
Shuttle.Agents The session's agents as a tree of threads.
Shuttle.Artifacts The tabbed pane: files, changes, previews, terminals, media, and any kinds you add.
Shuttle.Events The run's raw event history.
Shuttle.Palette The command palette.
Shuttle.SessionLayout Shuttle's own arrangement of all of the above, for when you want the whole thing.
Shuttle.Shell The frame with folders and sessions down the side. Leave it out if your app has its own navigation; nothing else needs it.

You can start with Shuttle.SessionLayout and take it apart later, or start from the individual parts. Both work with nothing above them but the provider.

A part of your own

useSession() returns what the stock parts read: the run id, the title, the status, the conversation feed, the agents and the raw events, and the agent thread that is open. A component of yours that calls it can sit anywhere inside <Shuttle.Session>. 

import { useSession } from '@swirls/shuttle/react'

function StatusStrip() {
  const { status, identities, events } = useSession()

  return (
    <div className="border-b px-3 py-1 text-[11px] text-muted-foreground">
      {status} · {identities.size} agents · {events.length} events
    </div>
  )
}

Your own kinds of tab

The artifacts pane knows only the kinds of tab it is given. Add yours to Shuttle's and it shows up in the pane's menu and in the command palette like any other. 

import { defaultArtifactTypes, type ArtifactType } from '@swirls/shuttle/react'

const designs: ArtifactType = {
  kind: 'acme:designs',
  label: 'Designs',
  icon: <PenTool size={14} />,
  launcher: { keywords: 'figma mockups', starter: true },
  needs: ['designs'],
  render: ({ tab, runId }) => <DesignBoard runId={runId} id={tab.target} />,
}

<Shuttle.Session id={sessionId} artifactTypes={[...defaultArtifactTypes, designs]}>
  • Name your kinds namespace:name, as in acme:designs, so they never collide with Shuttle's.
  • The backend keeps your tabs, with their title and target, without knowing what they show. What target means (an id, a URL, a path) is up to you.
  • needs names the API modules the tab depends on. Until the backend says it serves them, the kind is left out of the session, the menu and the palette. Leave it out for a tab that needs nothing from the backend. See What the backend serves.
  • single: true keeps one tab of the kind at most. Leave launcher out to open tabs only from your own code, such as a link in a message.
  • Someone who opens the session in an app that doesn't have your kind sees a note saying so, not an empty pane.

Watching a session

readOnly shows a session without the means to change it. The composer draws nothing, and the agents' questions and pull request proposals are shown but cannot be answered. Use it for a page that watches a session someone or something else is driving, such as one your backend started on its own. 

<Shuttle.Session id={runId} readOnly={!mayDrive}>
  <Shuttle.Conversation />
  <Shuttle.Composer />
</Shuttle.Session>

Fitting it into your app

The parts never assume where they are running. Your app gives them three things.

The host

createShuttleHost is called once, outside React, so your route loaders and the parts share one client and one cache. Everything about reaching the backend is an option here; the parts read no environment of their own. 

const host = createShuttleHost({
  baseUrl: 'https://engine.example.com/shuttle',
  headers: () => ({ authorization: `Bearer ${currentToken()}` }),
})
Option What it does
baseUrl Where the backend is, path included if it is mounted under one. Left out, it is the page's own origin.
headers Asked before every request that can carry a header (the API, signals, a run's log, uploads) and added to it. Make it read your newest token, so a renewed token never reconnects the session.
fetch Makes every HTTP request, for anything headers can't do.
grants Whether a run's live log is opened with a read grant. Left out, it is on exactly when the backend is on another origin. See A backend elsewhere.
previewPort The port sandbox previews are served on, when a development server sits in front of the backend.
runStore Added to how a run's event store is opened: an observer, another cache.

The router

Parts link to destinations, never to paths: { page: 'session', sessionId }, { page: 'home' } and so on. Your router says where each one is in your app, and location says which one is on screen, or null when it is none of Shuttle's. Here is the whole adapter for an app with a single page: 

const router: ShuttleRouter = {
  Link: ({ to, ...rest }) => (
    <a {...rest} href={to.page === 'session' ? `?session=${to.sessionId}` : '#'} />
  ),
  navigate: () => {},
  location: { page: 'session', sessionId },
}

A session shown inside a page about something else, with no Shuttle pages around it, can render every link as plain text and give location: null.

Who is signed in

identity is the signed-in person, their organization and the organization's runs, plus a way to list the people in it for names and sharing. Shuttle's own Worker says who is signed in at GET /me: 

const tenant = useQuery({ queryKey: ['me'], queryFn: () => host.client.tenant.me() }).data
const identity = tenant ? { tenant, listPeople: async () => [] } : null

A backend of your own that serves sessions only (no /me, no workspace) gets the tenant from sessionTenant, built from what your app already knows about the person. It names the organization's runs the way the engine does, and gives pulls as null, so the parts that read the pull request inbox show nothing from it. 

import { sessionTenant } from '@swirls/shuttle/api'

const identity: ShuttleIdentity = {
  tenant: sessionTenant({ user: { id: me.id, name: me.name, email: me.email }, orgId }),
  listPeople: async () => [],
}

role is member unless you give another. Pass runNames if your engine renames its runs with SHUTTLE_WORKSPACE_RUN_ID or SHUTTLE_PLAYBOOK_RUN_ID.

connectGithub, when given, sends the person off to connect their own GitHub account for what is done in their name. Without it the parts only say the account is not connected.

A backend elsewhere

When the backend is on the page's own origin, its cookie does everything. When it is somewhere else, such as an engine your product runs beside its own app:

  • Credentials go in headers. The parts also ask the browser to send the backend's cookie. An image, a download and a terminal are addresses the browser opens by itself and carry no header, so those need the cookie, or are left out.
  • The live log uses a grant. A WebSocket cannot carry a header, so for each run the parts ask the backend for a short-lived read grant (POST /runs/:id/grant), open the log with it, and renew it before it runs out. The backend gives grants when it is served with a grantSecret.
  • The backend lists your origin. Its answers carry the headers a browser needs only for the origins it was given.

What the backend serves

A backend running the engine may serve only some of Shuttle's API. The parts read GET /capabilities once and leave out what is not there: no Terminal tab without the terminal module, no Media tab without the assets module, no Browser tab without previews. Your own kinds of tab take part the same way through needs. A backend that does not answer /capabilities is taken to serve everything. 

const capabilities = await host.capabilities()
// { modules: ['session', 'runs'], previews: false, grants: true }

Styles

The parts are styled with Tailwind CSS 4. Import the theme after Tailwind and it tells Tailwind to read the package's files, so there is nothing to add to your config. 

@import 'tailwindcss';
@import '@swirls/shuttle/react/theme.css';

What it needs

  • A Shuttle backend to talk to: Shuttle's own Worker in apps/worker (locally with bun run dev), or a Worker of yours that hosts the engine.
  • React 19, TanStack Query 5 and Tailwind CSS 4.
  • A bundler such as Vite.
